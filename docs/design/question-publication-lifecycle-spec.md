# 手動題目發布生命週期與圖片清理

狀態：已發布為 [GitHub Issue #7](https://github.com/CyberNovaPixelPulse/are-you-blind-game/issues/7)，標記 ready-for-agent；尚未實作。

## Problem Statement

出題者需要知道題目是否真的發布成功，並在網路中斷後安全繼續。目前手動發布由頁面協調審核、兩張圖片上傳、題目儲存及失敗清理；圖片分屬不同儲存區，清理卻只記錄路徑並使用同一儲存區，原圖可能殘留。伺服器已成立題目但回應遺失時，瀏覽器仍可能嘗試刪除正式題目使用的圖片；重新送出也可能建立重複題目。離頁、審核過期及清理失敗缺少一致的恢復規則。

## Solution

讓手動出題使用一致的發布生命週期。以伺服器確認題目正式成立作為成功依據；結果不明時先查明，未修改內容的重試屬同次發布。伺服器協調提交、取消及清理，保護正式題目的圖片。出題者可清楚區分正在發布、結果待確認、已發布、已取消及已過期，並在需要時明確選擇重審、重試或建立新發布。

## User Stories

1. As a 出題者, I want 從送出到結果確認有一致的發布流程, so that 我知道題目目前處於哪個階段。
2. As a 出題者, I want 題目真正成立後才被視為發布成功, so that 成功畫面代表題目確實可供遊玩。
3. As a 出題者, I want 圖片上傳完成與題目發布成功有所區別, so that 我不會誤以為只上傳圖片就完成出題。
4. As a 出題者, I want 斷線時先確認發布結果, so that 已成功的題目不會被誤判失敗。
5. As a 出題者, I want 未修改內容的重試沿用同次發布, so that 不會重複建立題目。
6. As a 出題者, I want 已成功的重試回傳原本結果, so that 我能安全確認先前的發布。
7. As a 出題者, I want 同次發布送出時固定內容, so that 伺服器成立的題目與我送出的版本一致。
8. As a 出題者, I want 修改前先查明原發布結果再建立新發布, so that 新舊內容不會混成一次提交。
9. As a 出題者, I want 切換介面語言不改變已送出的題目語言, so that 題目不會在發布途中被改成其他語言。
10. As a 出題者, I want 審核過期時先確認是否已發布, so that 不會為已成立的題目再次審核。
11. As a 出題者, I want 必要重審沿用同一份固定內容, so that 發布仍符合原本的題目版本。
12. As a 出題者, I want 完整且符合內容的已上傳圖片可被沿用, so that 重審不必重傳所有圖片。
13. As a 出題者, I want 重新審核由我明確啟動, so that 背景查詢不會反覆耗用審核資源。
14. As a 出題者, I want 結果不明時先有限次自動查詢, so that 短暫斷線可自行恢復。
15. As a 出題者, I want 自動確認仍無結果時可再次確認或提出取消, so that 我有明確的下一步。
16. As a 出題者, I want 結果不明時保留目前內容, so that 不會因暫時無法確認而失去這份題目。
17. As a 出題者, I want 結果不明時不被引導以新識別重送同一份題目, so that 不會建立重複題目。
18. As a 出題者, I want 取消與提交同時發生時得到一致結果, so that 題目不會同時被當成已發布與已取消。
19. As a 出題者, I want 題目已發布時取消回覆已發布, so that 我知道正式題目仍存在。
20. As a 出題者, I want 取消先成立後舊提交不能再發布, so that 我的取消選擇確實生效。
21. As a 出題者, I want 取消成立後即使圖片仍待清理也可繼續出題, so that 儲存服務暫時失敗不會阻擋我。
22. As a 出題者, I want 關閉分頁不會自動取消發布, so that 離頁不會破壞正在處理的題目。
23. As a 出題者, I want 未完成發布保留一段明確時間, so that 暫時中斷後仍有機會繼續處理。
24. As a 出題者, I want 已過期的發布可被辨識但不能重新啟用, so that 晚到請求不會意外成立題目。
25. As a 出題者, I want 仍保有完整內容時能明確建立新發布, so that 舊發布過期後仍可重新出題。
26. As a 玩家, I want 已成立題目的圖片不被失敗清理刪除, so that 遊玩時不會遇到因發布重試造成的破圖。
27. As a 維護者, I want 每張上傳圖片保有正確儲存區與路徑, so that 部分失敗時能清理正確資源。
28. As a 維護者, I want 未清完的資源可由伺服器持續重試, so that 不依賴出題者保持分頁開啟。
29. As a 維護者, I want 重複清理不存在的圖片仍算成功, so that 清理能安全重試。
30. As a 維護者, I want 到期清理避開正在提交或已被正式題目引用的圖片, so that 自動清理不破壞有效題目。
31. As a 維護者, I want 保留最小發布結果紀錄, so that 可拒絕過期或取消後的晚到請求而不保存整份草稿。
32. As a 維護者, I want 從發布流程公開介面驗證失敗與競爭情境, so that 更換內部實作時仍能確保行為正確。

## Implementation Decisions

- 建立具實質責任的發布流程模組，協調審核、圖片上傳、題目儲存、結果確認與補償清理。頁面保留表單、裁切操作及進度顯示；伺服器保有發布資格及清理資格判定。第一個接入者是手動發布，自動發題保留既有流程。
- 題目發布成功指伺服器確認題目已正式成立；不是圖片上傳完成、HTTP 回應到達或成功畫面顯示。成功後的本機偏好儲存或畫面處理失敗不得撤銷題目或清理其圖片。
- 同次發布具有穩定識別及固定內容，包含圖片、裁切範圍、答案、選項、作者名稱與題目語言。相同識別不得接受不同內容；未修改的重試沿用該識別，已成功則回傳原結果，不再建立題目。修改前須查明原結果，再建立新發布。介面翻譯切換不改動已送出內容。
- 公開操作需涵蓋開始／繼續發布、查詢結果、提出取消及明確重審；結果能區分進行中、結果未確認、已發布、已取消與已過期，並表達是否尚待清理或需重新審核。具體命名與資料結構由實作決定。
- 發布狀態及最終結果須能跨請求保存；並行重試、提交、取消與到期處理須由伺服器協調，不能僅依賴瀏覽器鎖或單行程記憶體。發布先成立則取消回覆已發布；取消先成立則提交不得成立；結果不明或正在提交時暫緩清理。結果確認必須與題目的實際成立狀態一致。
- 每張圖片的資源身分包含儲存區、路徑及所屬發布，正確區分裁切圖與原圖。伺服器清理前確認圖片屬於該次發布且未被正式題目引用；瀏覽器不得以提交回應失敗為由直接刪圖。沿用現有登入、所有權及審核內容綁定檢查。
- 部分上傳失敗亦由伺服器追蹤與處理，包含圖片實際上傳完成但成功回應遺失的情況，不能僅以瀏覽器已收到的成功路徑清單為依據。
- 審核證明過期時先查發布結果。已成功直接回傳原結果；確認未成功且證明過期才重新審核同一份固定內容。仍完整且符合內容的已上傳圖片可沿用；查詢不觸發審核，需要重審時由使用者明確選擇重新審核並繼續。
- 結果未確認時顯示正在確認發布結果並進行有限次自動查詢；仍不明時提供再次確認與取消這次發布，保留目前內容，暫不允許以新識別重送同一份題目。提出取消不代表取消立即成立，仍需回傳伺服器協調後的結果。
- 離頁或關閉分頁不視為取消，不依賴離頁通知完成清理。未完成發布自最後一次有效操作起保留 24 小時；有效操作包括成功上傳、重新通過審核與繼續提交，單純查詢不延長期限。到期後排程清理仍須遵守提交與正式引用保護，不能僅憑時間直接刪圖。
- 取消成立與資源清理完成分開。取消後不能再提交，即使暫存圖片尚未清完，使用者仍可繼續出題；顯示已取消、暫存圖片將由系統清理。未清完資源須持久記錄並重試，不存在的圖片視為已清理；失敗不恢復發布資格，也不要求使用者逐張處理。
- 到期後標為已過期；最小結果紀錄暫不自動刪除，僅保存辨識該次發布及最終結果所需資訊，不保留完整草稿或圖片。舊識別不得重新啟用；使用者仍保有完整內容時可明確建立新發布，重新上傳並審核。
- 沿用現有審核標準、題目規則與圖片限制。可新增支援跨請求狀態、唯一性及清理追蹤所需的持久化結構、流程 API 與排程；具體介面命名、排程頻率、有限查詢次數與間隔依上述行為決定，部署不屬本規格交付。

## Testing Decisions

- 已獲使用者確認：發布流程公開介面為唯一主要自動化測試邊界，以可控制結果與回應順序的審核、儲存及圖片服務替身驗證外部結果，不測私有狀態、內部函式呼叫次數或每個輔助函式。
- 覆蓋部分上傳失敗、上傳成功但回應遺失、圖片儲存區辨識、提交成功但回應遺失、相同內容重試不重複發題、不同內容不得沿用同識別，以及正式題目圖片不被清理。
- 覆蓋提交／取消／到期清理競爭、結果不明與仍在提交的保護、取消後清理部分失敗及重試、重複刪除、24 小時期限與有效操作延長規則、查詢不延長期限、已過期及已取消識別的晚到請求。
- 覆蓋審核過期先查結果、成功不重審、必要時明確重審及圖片沿用、固定內容與題目語言不受介面語言切換影響，以及成功後的本機儲存／畫面失敗不撤銷題目。
- 關鍵競爭保證需經同一公開介面搭配實際持久化實作驗證，不能只以單行程替身測試宣稱跨請求唯一性已成立；外部圖片與審核服務可受控，不必呼叫付費審核。
- 另以少量手動發布頁整合驗收確認進度、結果待確認、再次確認、明確重審、取消、過期後建立新發布及成功畫面；不驗收自動發題或關閉分頁後整份編輯表單恢復。
- 專案已有 Node test runner 搭配 tsx 的公開介面行為測試，以及以 Playwright 在 HTTP 邊界控制回應的瀏覽器測試，可沿用既有測試指令與模式，無須另立測試框架。

## Out of Scope

- 自動發題流程接入或重寫。
- 關閉分頁後恢復整份編輯表單、跨裝置草稿同步或完整草稿保存。
- 審核模型、通過標準、品質評分、圖片限制與題目內容規則重新設計。
- 題池、答案判定、計分、廣告及遊戲模式流程調整。
- 已發布題目的編輯、刪除或下架流程重新設計。
- 歷史圖片的全面盤點與清理；本規格清理範圍為新生命週期所追蹤的手動發布資源。
- 部署、資料庫正式環境遷移執行與正式環境排程啟用。

## Further Notes

- 本規格整理本次討論已逐項確認的十四項決策與測試邊界。使用者要求轉為規格並發布，目前尚未實作。
- 既有發布與圖片相關程式包含尚未提交的修改；實作前須檢查實際狀態並保留無關修改，遵守專案代理指引與所用版本文件。
- 實作拆票應維持可驗收的完整使用者路徑；圖片刪除前的結果確認、引用保護與提交／取消協調是同一組一致性要求，不能以瀏覽器端補償代替。

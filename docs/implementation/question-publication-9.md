# Issue #9 — 取消發布與伺服器清理

工單：https://github.com/CyberNovaPixelPulse/are-you-blind-game/issues/9 。父規格 #7；#10 明確重審與 #11 到期處理仍不在本次範圍。

## 交付

- 取消與提交沿用同一發布資料列鎖。取消可先於 begin 建立不可重啟的終態；發布先成立回覆已發布，取消先成立拒絕晚到提交及新上傳意圖。
- 瀏覽器先確認目前結果，再要求伺服器取消。結果不明保留固定內容；伺服器確認已取消後即可繼續出題，不等待圖片清理或舊上傳請求結束。被拒絕的發布也須先取得取消裁決，不能直接丟棄識別後留下未追蹤圖片。
- 每張圖片的儲存區、路徑與待清理狀態沿用持久化意圖。清理工作者以租約領取有限批次，刪除失敗／結果回寫失敗可恢復，不存在的物件視為成功。
- 清理前檢查題目與私有答案表的正式引用。新的圖片引用與取消使用同一父資料列鎖，防止檢查後才建立引用。既有正式引用保留，無關欄位更新不受影響。
- 保留已取消圖片清單供後續巡查，即使取消前已發出的上傳晚於首次清理才抵達，仍可被下一次工作者移除。這不是歷史圖片全面清理，也不處理未取消發布的到期。

## 正式環境前提

先依序套用 #8 與本次 migration：

1. `20261026110107_question_publication_lifecycle.sql`
2. `20261026132427_publication_cancellation_cleanup.sql`

受保護的工作者入口為 `/api/cron/publication-cleanup`，只接受與 `CRON_SECRET` 相符的 Bearer header，使用伺服器 service role 操作。部署設定包含每天 01:00 UTC（台北 09:00）的 Vercel Cron；此處只新增設定，沒有設定正式 secret、執行 migration、部署或啟用正式排程。

失敗資源五分鐘後可重新領取；成功刪除及正式引用受保護的清單二十四小時後可再次巡查。實際自動執行由每日排程驅動，沒有承諾五分鐘內完成。單次最多五批、每批五十項；優先處理從未領取及最久未領取的資源，到期時間只決定是否可領取，避免舊失敗項目耗盡每日預算而餓死新資源。掃描筆數與可刪資源分開計算，不因整批受保護就誤判佇列耗盡。每筆 Storage 操作最多五秒，工作者以四十五秒工作預算避免用盡平台期限，超出容量或中途終止的工作留待後續執行。

## 驗證

- 共用發布流程測試：上傳期間取消、發布已成立、取消結果不明與終態重試。
- 真正 PostgreSQL、獨立連線驗證兩種鎖競爭結果、取消後直接 SQL 晚到提交、取消先於 begin、公開角色拒絕操作。
- 以儲存邊界替身驗證正確儲存區、部分上傳成功但回應與讀回皆失敗、部分刪除失敗與重試、不存在物件、晚到寫入再清理、私有正式引用與新增引用防護、並行工作者不重複領取。
- 瀏覽器驗證取消成功、其實已發布、結果未確認與發布被拒絕四個情境；確認不由瀏覽器刪圖，清理待完成仍可立即繼續編輯。
- 背景入口以真正 route handler 驗證無身分拒絕與無瀏覽器登入的佇列執行。

資料庫測試使用最小題目／私有答案表 fixture，未代表所有正式 Supabase triggers 與外部 Storage 的完整上線驗收。出題頁面既有 AI 選項身分驗證變更經使用者同意保留，未混入本次提交。
